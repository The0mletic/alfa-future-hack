# Агент релевантности: текущий запуск

Готовы контракт, сборка входа и инструменты прямых контрагентов. Ранжирования, вызовов LLM и загрузки статей ещё нет.

## Подготовка окружения

Команды выполняются из корня проекта. Зависимости устанавливаются только в нашу папку:

```sh
python3 -m venv relevance_agent/.venv
relevance_agent/.venv/bin/python -m pip install -r relevance_agent/requirements.txt
```

Окружение не было установлено автоматически. Проверки выполнялись на Python из среды разработки с Pydantic 2.14.1.

## Собрать вход

```sh
relevance_agent/.venv/bin/python -B -m relevance_agent.build_input \
  --company-id U_57706 \
  --news relevance_agent/examples/news.synthetic.json \
  --as-of 2026-10-26T12:00:00+03:00 \
  --output relevance_agent/runs/input.json
```

Это реальный профиль и **учебная новость**, не настоящая подборка. Уже проверенный результат находится в `examples/assembled_input.synthetic_news.json`. Его не следует принимать за результат работы агента: это только вход.

Для реальных данных замените --news на файл, созданный RSS-парсером с --format json --output. Парсер запускается отдельно; здесь сетевых запросов нет. Сборщик принимает как обёртку `{generated_at,count,items}`, так и JSON-список новостей. Формат дат и исходные ID сохраняются; новости не сортируются, не обрезаются и не отбрасываются молча.

По умолчанию профили читаются из `applications/filtered_data/company_profiles.jsonl`, путь определяется относительно кода, а не текущей директории. Другой файл задаётся через --profiles. Для выбора только целевой выборки можно передать company_profiles_target.jsonl.

Подготовленная аналитика подключается через `--bank-materials relevance_agent/data/bank_materials.json`. Это JSON-список BankMaterial из CONTRACT.md, с текстом и номерами страниц. Файл пока не создан, тексты нужно подготовить разово. Без параметра используется пустой список с предупреждением. Если параметр указан, а файла нет или он испорчен, сборка завершается ошибкой.

Другие параметры:

- --request-id: идентификатор запуска, по умолчанию новый UUID.
- --as-of: момент оценки с часовым поясом, по умолчанию текущее UTC. Время generated_at из парсера не подменяет момент оценки.
- --top-k: максимальное число выбранных новостей будущего агента, по умолчанию 5; сборщик не сокращает входной список до этого числа.
- --output: новый файл только внутри relevance_agent. Существующие файлы не перезаписываются. Без параметра JSON выводится в stdout.

Диагностика идёт в stderr, чтобы не смешиваться с JSON. Код завершения: 0 при успехе, 2 при ошибке. Пустой список новостей допустим. Отсутствие summary/даты/ссылки и будущие относительно as_of публикации отмечаются предупреждениями; решения об их оценке остаются за агентом.

## Вызов из Python

```python
from relevance_agent.build_input import build_relevance_input

request = build_relevance_input(
    company_id="U_57706",
    news_path="relevance_agent/examples/news.synthetic.json",
    as_of="2026-10-26T12:00:00+03:00",
)
# request — проверенный RelevanceInput.
# request.model_dump() — словарь; request.model_dump_json() — JSON-текст.
```

Сборщик не меняет исходные файлы. Профиль сохраняется целиком; адаптер проверяет основные блоки, но не доказывает истинность всех их значений. Неполноту внутри профиля нужно учитывать на этапе анализа.

## Прямые контрагенты (реализовано)

```python
from relevance_agent.counterparties import CounterpartyTools

tools = CounterpartyTools()  # один экземпляр на запуск
links, profiles = tools.collect_context("U_57706")
# Или по отдельности:
links = tools.get_counterparties("U_57706")
profile = tools.get_company_profile("U_237002")
```

```sh
relevance_agent/.venv/bin/python -B -m relevance_agent.counterparties --company-id U_57706
```

Команда выводит JSON с links и profiles в stdout, краткую статистику в stderr. Файлы не записывает. Можно передать --payments, --companies, --profiles для другого набора.

- Суммируются все прямые связи из CSV, включая повторные строки одного направления. Самоплатежи исключаются. Одна компания может быть одновременно получателем и отправителем.
- Доля считается отдельно по входящим/исходящим суммам, без округления до целых процентов; при нулевом знаменателе null. Это доля наблюдаемых платежей, не всего бизнеса.
- Профили: full — готовый JSONL; partial — исходные сведения CSV (ОКВЭД, выручка, штат, география, ФТС, группа, raw); unavailable — сведений нет либо исходные строки противоречат друг другу. Полноценные чувствительности в partial не выдумываются.
- Некорректные суммы/счётчики в связях целевой компании исключаются с предупреждением и complete=false. Неизвестные участники платежей также делают покрытие неполным. Отсутствующий/нечитаемый файл — ошибка, не пустая выборка.
- Платежи читаются один раз на target для экземпляра инструмента; профили и таблица компаний индексируются лениво один раз. Возвращаемые копии защищают кэш от случайного изменения вызывающим кодом. Для обновлённых файлов нужен новый экземпляр.
- Обход строго на один уровень. Получение профиля контрагента не загружает его платёжные связи.
- links и profiles передаются в validate_exchange для проверки counterparty_evidence. Во вход v1 новые поля не добавлялись: это результаты инструментов будущего агента.

Проверено на U_57706: 7 направленных связей, 5 уникальных контрагентов, 2 partial и 3 unavailable; входящие 94 967 000 ₽, исходящие 644 687 000 ₽. Суммы совпадают с подготовленным профилем. Локальная проверка заняла около секунды (не гарантия производительности). Все 34 теста прошли.

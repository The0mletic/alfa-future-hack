# Агент релевантности: текущий запуск

> Актуальное решение: первичный ранжировщик не читает и не ищет аналитику Альфа-Банка
> и не отправляет её модели. Аналитика остаётся для следующего агента.
> `bank_materials`, `bank_metadata` и `bank_evidence` сохраняются в выходной схеме
> ради совместимости, но в новых результатах ранжирования пусты. Непустые ссылки
> на аналитику не проходят проверку. Старые разделы о поиске описывают сохранённый
> инструмент knowledge.py и прежние прогоны, а не текущий обязательный пайплайн.



## Основной запуск: одна новость → один клиент

Настройки в `relevance_agent/.env` (файл игнорируется Git):

```dotenv
RELEVANCE_BASE_URL=https://АДРЕС-ПРОВАЙДЕРА/v1
RELEVANCE_MODEL=ТОЧНЫЙ-ID-РАЗРЕШЕННОЙ-МОДЕЛИ
RELEVANCE_API_KEY=ВАШ-КЛЮЧ
```

Шаблон — `.env.example`. Провайдер не выбран автоматически. Адаптер `model.py`
использует LangChain ChatOpenAI для совместимого Chat Completions API. Совместимость
конкретного endpoint нужно подтвердить живым запросом; расширения провайдера не используются.

```bash
relevance_agent/.venv/bin/python -B -m relevance_agent.run \
  --company-id U_57706 \
  --news relevance_agent/examples/news.synthetic.json \
  --news-id demo_news_01 \
  --output relevance_agent/runs/first.json
```

Этот пример содержит **синтетическую новость**. Для рабочего запуска подставьте JSON
RSS-парсера и ID одной новости. Остальные новости файла в контекст модели не попадают.
CLI создаёт новый файл только внутри relevance_agent; `not_scored` даёт код выхода 2.

Программный вход: `SingleNewsInput(company_id=..., news=NewsItem(...))`;
вызов: `score_news(request, model)` из `relevance_agent.graph`.
Для серии событий можно один раз создать `graph = build_graph(model)` и вызывать
`graph.invoke({"request": request})["output"]`; контекст LLM между вызовами не накапливается,
справочники контрагентов кэшируются. После обновления датасета создайте новый граф.

Результат `SingleNewsOutput` содержит одну оценку и весь использованный контекст для
следующего агента. `assessment.relevance_score` — абсолютный балл 0–100; ранга и
автоматического бизнес-порога отбора нет. При ошибке `assessment=null`, `status=not_scored`.
Старые пакетные схемы ниже сохранены для совместимости; новый граф их не принимает.

Граф — базовый фиксированный процесс с условным повтором проверки, пока без LLM-планировщика
поиска. Он читает всех доступных прямых контрагентов и делает до двух вызовов модели
(один основной, один — только если после ремонта ответ всё равно невалиден).
Банковская аналитика на этапе отбора не ищется и не передаётся.
При таймауте модели выполняется ровно один повторный вызов; другие сетевые ошибки
не повторяются. Ответ ограничен 3000 токенами,
контекст — 120000 символами: при превышении возвращается not_scored без молчаливого
отбрасывания контрагентов. Это технический лимит, не гарантия вместимости конкретной модели.

Балл считает код по каналам влияния (scoring.py, подробно — CONTRACT.md, channels-v3):
модель называет каналы, силу шока, горизонт и механизм, код умножает на подверженность
компании из профиля и на достоверность события, объединяет каналы noisy-OR с затуханием
для второго и третьего канала. Модель балл не ставит.

Основная модель — deepseek/deepseek-v4.1-flash (решение пользователя 26.10.2026; в
relevance_agent/.env). GLM-5.3-Flash на этом шаге расходует весь лимит 3000 токенов на
рассуждения, Qwen3.6 работает, но вдвое медленнее (checks/live_news_channels/REPORT.md).

Быстрый режим (запрос к модели):

- В модель уходят компактные карточки, а не полные объекты. Карточка компании —
  подмножество полного профиля с теми же путями (`PROFILE_DROP` в graph.py): удалены
  raw, data_quality, summary, news_keywords, дубль контрагентов, банковский статус клиента,
  source_fields/news_keywords внутри sensitivities. Любой JSON Pointer из карточки
  разрешается в полном профиле, поэтому validate_exchange не менялся.
- Контрагенты сгруппированы по ID: связи (направление, сумма, число, доля до 3 знаков)
  и сокращённый профиль либо null. Абсолютные пути к CSV в модель не передаются.
- Новость — одна карточка: текст статьи, а summary только если он не входит в текст.
- Общие ограничения данных (период платежей, роль по направлению, полнота парсера)
  модели не передаются и не генерируются ею: они добавляются в warnings кодом.
- Ответ: reason до 300 символов, не больше 4 каналов и 2 ограничений; вместо JSON Schema
  в prompt — короткий JSON-шаблон.
- Ремонт без повторного вызова: каналы с неверными полями и каналы через контрагентов
  без связи/профиля отбрасываются, доля берётся из инструмента, JSON извлекается из
  Markdown-обёртки. Что отброшено — записывается в warnings. Повтор только если JSON
  не разобран или ни один из названных каналов не прошёл проверку.

На трёх новостях checks/live_news вход сократился с 27–28,5 тыс. до 10,6–12 тыс. символов
(`python -B -m relevance_agent.checks.measure_payload`, без сети и LLM). Ускорение в секундах
и качество ответа после изменений пока не измерялись живым прогоном.
Использованные токены записываются, если провайдер их возвращает; стоимость не вычисляется.

knowledge.py (лексический поиск по аналитике) сохранён для следующего агента, но граф
отбора его не вызывает. Проверка ссылок доказывает наличие источника, но не истинность
объяснения модели. Для бизнес-калибровки нужна ручная проверка оценок.

Проверено: 58 тестов; реальный U_57706 → 7 связей, 5 контрагентов, 5 фрагментов банка.
В `checks/graph.synthetic_model.json` сохранён **технический прогон с подставным ответом
модели и синтетической новостью**, не результат реальной оценки. Настоящий провайдер ещё
не вызывался. API сверены с [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api)
и [LangChain ChatOpenAI](https://docs.langchain.com/oss/python/integrations/chat/openai).

Готов базовый LangGraph для независимой оценки одной новости одному клиенту: профиль → прямые контрагенты → статья и аналитика → модель → проверка ответа. Реальный вызов провайдера ещё не проверен: нужны endpoint, точный model ID и ключ.

## Подготовка окружения

Команды выполняются из корня проекта. Зависимости устанавливаются только в нашу папку:

```sh
python3 -m venv relevance_agent/.venv
relevance_agent/.venv/bin/python -m pip install -r relevance_agent/requirements.txt
```

Окружение relevance_agent/.venv создано и зависимости установлены. Для другой машины используйте команды выше.

## Собрать вход

```sh
relevance_agent/.venv/bin/python -B -m relevance_agent.build_input \
  --company-id U_57706 \
  --news relevance_agent/examples/news.synthetic.json \
  --as-of 2026-10-26T12:00:00+03:00 \
  --output relevance_agent/runs/input.json
```

Это реальный профиль и **учебная новость**, не настоящая подборка. Уже проверенный результат находится в `examples/assembled_input.synthetic_news.json`. Его не следует принимать за результат работы агента: это только вход.

Для реальных данных замените --news на файл, созданный RSS-парсером с --format json --output. Парсер запускается отдельно; здесь сетевых запросов нет. Сборщик принимает как обёртку `{generated_at,count,items}`, так и JSON-список новостей. Формат дат и исходные ID сохраняются; новости не сортируются, не обрезаются и не отбрасываются молча.

По умолчанию профили читаются из `applications/filtered_data/company_profiles.jsonl`, путь определяется относительно кода, а не текущей директории. Другой файл задаётся через --profiles. Для выбора только целевой выборки можно передать company_profiles_target.jsonl.

Подготовленная аналитика подключается через `--bank-materials relevance_agent/data/bank_materials.json`. Это JSON-список BankMaterial из CONTRACT.md, с текстом и номерами страниц. Это ручной путь для старого пакетного сборщика; новый граф автоматически использует готовую applications/knowledge_base/chunks.jsonl. Без параметра используется пустой список с предупреждением. Если параметр указан, а файла нет или он испорчен, сборка завершается ошибкой.

Другие параметры:

- --request-id: идентификатор запуска, по умолчанию новый UUID.
- --as-of: момент оценки с часовым поясом, по умолчанию текущее UTC. Время generated_at из парсера не подменяет момент оценки.
- --top-k: максимальное число выбранных новостей будущего агента, по умолчанию 5; сборщик не сокращает входной список до этого числа.
- --output: новый файл только внутри relevance_agent. Существующие файлы не перезаписываются. Без параметра JSON выводится в stdout.

Диагностика идёт в stderr, чтобы не смешиваться с JSON. Код завершения: 0 при успехе, 2 при ошибке. Пустой список новостей допустим. Отсутствие summary/даты/ссылки и будущие относительно as_of публикации отмечаются предупреждениями; решения об их оценке остаются за агентом.

## Вызов из Python

```python
from relevance_agent.build_input import build_relevance_input

request = build_relevance_input(
    company_id="U_57706",
    news_path="relevance_agent/examples/news.synthetic.json",

# request — проверенный RelevanceInput.
# request.model_dump() — словарь; request.model_dump_json() — JSON-текст.
```

## Прямые контрагенты (реализовано)

```python
from relevance_agent.counterparties import CounterpartyTools

tools = CounterpartyTools()  # один экземпляр на запуск
links, profiles = tools.collect_context("U_57706")
# Или по отдельности:
links = tools.get_counterparties("U_57706")
profile = tools.get_company_profile("U_237002")
```

```sh
relevance_agent/.venv/bin/python -B -m relevance_agent.counterparties --company-id U_57706
```

Команда выводит JSON с links и profiles в stdout, краткую статистику в stderr. Файлы не записывает. Можно передать --payments, --companies, --profiles для другого набора.

- Суммируются все прямые связи из CSV, включая повторные строки одного направления. Самоплатежи исключаются. Одна компания может быть одновременно получателем и отправителем.
- Доля считается отдельно по входящим/исходящим суммам, без округления до целых процентов; при нулевом знаменателе null. Это доля наблюдаемых платежей, не всего бизнеса.
- Профили: full — готовый JSONL; partial — исходные сведения CSV (ОКВЭД, выручка, штат, география, ФТС, группа, raw); unavailable — сведений нет либо исходные строки противоречат друг другу. Полноценные чувствительности в partial не выдумываются.
- Некорректные суммы/счётчики в связях целевой компании исключаются с предупреждением и complete=false. Неизвестные участники платежей также делают покрытие неполным. Отсутствующий/нечитаемый файл — ошибка, не пустая выборка.
- Платежи читаются один раз на target для экземпляра инструмента; профили и таблица компаний индексируются лениво один раз. Возвращаемые копии защищают кэш от случайного изменения вызывающим кодом. Для обновлённых файлов нужен новый экземпляр.
- Обход строго на один уровень. Получение профиля контрагента не загружает его платёжные связи.
- links и profiles передаются в validate_exchange для проверки counterparty_evidence. Во вход v1 новые поля не добавлялись: это результаты инструментов будущего агента.

Проверено на U_57706: 7 направленных связей, 5 уникальных контрагентов, 2 partial и 3 unavailable; входящие 94 967 000 ₽, исходящие 644 687 000 ₽. Суммы совпадают с подготовленным профилем. Локальная проверка заняла около секунды (не гарантия производительности). Все 34 теста прошли.

## Полный текст статьи (реализовано)

```python
from relevance_agent.articles import ArticleTools

# request — результат build_relevance_input().
with ArticleTools(request.news, request.options) as tools:
    article = tools.fetch_article(request.news[0].id)
    # article.status: ok или unavailable; текст в article.text.
```

CLI принимает ранее собранный вход и ID новости (ссылка берётся только из этого входа):

```sh
relevance_agent/.venv/bin/python -B -m relevance_agent.articles \
  --input relevance_agent/runs/input.json --news-id NEWS_ID
```

Возвращает ArticleResult как JSON в stdout. Код завершения 0 — текст получен, 1 — источник недоступен/лимит, 2 — неверный вход. Учебный example.com из examples не является настоящей статьёй.

Как работает: проверка публичного HTTP(S)-адреса → загрузка с ручной проверкой каждого перенаправления → поиск articleBody/article/main или блока абзацев → очистка меню и служебных элементов → ограничение текста. Доступны обычные HTML-страницы; JavaScript, OCR, PDF и обход платного доступа не поддерживаются. Эвристика не гарантирует, что извлечена вся статья: сайт может вернуть доступный анонс. status=ok означает наличие извлечённого текста, а не доказанную полноту или достоверность.

Параметры из RunOptions: max_article_fetches (по умолчанию 15 попыток разных URL) и max_article_chars (20 000 символов). Дополнительно: страница до 2 МБ, до 5 редиректов, таймаут сетевой операции до 10 секунд, проверяемый бюджет времени 25 секунд. DNS-разрешение системное, не имеет жёсткого общего дедлайна; текущая сетевая операция также может закончиться позже общего бюджета до своего таймаута. Ответы со сжатием отклоняются, если сервер проигнорировал Accept-Encoding: identity.

Текст ограничивается с truncated=true. Ошибка, превышение лимита, неподдерживаемый формат или слишком короткий текст дают unavailable с error; исходный summary не изменяется и не подставляется в поле полного текста. Кэш, включая ошибки, действует в пределах экземпляра инструмента; для новой попытки нужен новый экземпляр. Совпадающие URL не расходуют бюджет повторно. Неизвестный news_id — ошибка вызова.

Частные, локальные и служебные IP запрещены, включая цели редиректов. Соединение привязано к проверенному IP с сохранением Host и TLS SNI/проверки сертификата. Переменные окружения прокси не используются. Инструмент не отправляет профили компании: только HTTP GET по ссылке источника. Содержимое статьи остаётся недоверенным текстом для будущего prompt.

Зависимости установлены в relevance_agent/.venv. Весь набор из 47 тестов прошёл, включая HTML, кириллицу Windows-1251, ошибки HTTP, таймаут, размеры, редиректы, блокировку локальных адресов и кэш. Сетевая проверка пресс-релиза ЦБ завершилась ConnectTimeout; затем успешно проверены Коммерсантъ и CNews (см. checks/REPORT.md). Автотесты транспорта используют подставные HTTP-ответы, не сеть.

Документация библиотек: [HTTPX](https://www.python-httpx.org/quickstart/), [Beautiful Soup](https://www.crummy.com/software/BeautifulSoup/bs4/doc/).


Живая проверка на четырёх источниках завершена: Коммерсантъ и CNews — текст получен; ЦБ — таймаут; Интерфакс — HTML без статьи. Ошибка выбора блока Коммерсанта исправлена, добавлен тест. Всего 48 тестов прошли. Подробности: checks/REPORT.md. Это проверка отдельных URL, не всех страниц источников.


## Совместимость с новым полным RSS-парсером

Подтянуто обновление команды `3d5564d`: `scripts/rss_full_parser.py` возвращает
`{generated_at, total_sources, total_items, sources: [{source, feed_url, items}]}`.
`load_news()` теперь принимает и этот формат. Старый формат и список NewsItem поддерживаются.

Адаптер в `parser_adapter.py` переносит source из группы, summary_rss → summary,
сохраняет full_text и создаёт id = первые 16 hex-символов SHA-1 ссылки после strip/lower,
как в прежнем RSS-парсере. content_for_llm проверяется на соответствие full_text или
summary_rss, но не выдаётся за самостоятельный полный текст. Счётчики, даты и повторы
проверяются; дубли ID вызывают явную ошибку, автоматически не объединяются.

Если full_text непустой, ArticleTools использует его без сетевого запроса, ограничивая
длину max_article_chars. Результат: text_source=upstream_parser, final_url=null — новый
парсер не сообщает конечный URL редиректа. Полнота извлечения не гарантируется.
Если full_text пустой, сохраняется наш прежний путь загрузки статьи.
В запрос LLM текст попадает один раз — в news.text карточки новости.

Для запуска используйте прежнюю команду relevance_agent.run, передав новый JSON
через --news. Посмотреть присвоенные ID можно без сети:

```bash
relevance_agent/.venv/bin/python -B -c 'from relevance_agent.loaders import load_news; print([(n.id, n.title) for n in load_news("relevance_agent/rss_full_report.json")])'
```

Для запуска самого командного парсера из корня нужно явно указать
`--feeds-file scripts/feeds.txt` и `--output relevance_agent/rss_full_report.json`:
путь feeds.txt у него считается относительно текущего каталога. Его зависимости
устанавливайте в локальное окружение. На снимке 3d5564d в общем requirements.txt
отсутствует обязательная trafilatura; сам парсер в этой проверке не запускался.
Наш адаптер не импортирует парсер и не требует его дополнительных библиотек.

65 тестов прошли, включая новый формат, отсутствие повторной загрузки, резервный путь,
ограничение длины и передачу текста модели ровно один раз. Платных вызовов не было.

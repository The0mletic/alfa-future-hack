# Контракт агента релевантности v1.0

> Актуальное решение: первичный ранжировщик не читает и не ищет аналитику Альфа-Банка
> и не отправляет её модели. Аналитика остаётся для следующего агента.
> `bank_materials`, `bank_metadata` и `bank_evidence` сохраняются в выходной схеме
> ради совместимости, но в новых результатах ранжирования пусты. Непустые ссылки
> на аналитику не проходят проверку. Старые разделы о поиске описывают сохранённый
> инструмент knowledge.py и прежние прогоны, а не текущий обязательный пайплайн.


Статус: пакетный контракт сохранён для совместимости. Основной событийный контракт описан ниже. Формат предложен для интеграции; согласование с товарищами ещё впереди. Загрузчики и сборщик входа реализованы на этапе 2; инструменты контрагентов — в counterparties.py. Получение статей реализовано в articles.py. Поиск аналитики, адаптер модели и базовый граф реализованы; живой LLM-вызов ожидает настройки провайдера.

## Как читать файлы

- `contracts.py` — источник истины: Python-модели Pydantic и проверки связности.
- `schemas/*.json` — экспорт JSON Schema для участников на других языках.
- `examples/input.json`, `examples/output.json` — парный синтетический пример. Балл написан вручную; это не прогноз и не результат модели. Банковских цитат в примере нет.
- `tests/test_contracts.py` — проверка правил контракта без сети и LLM.

Контракт отвечает на вопрос «что передаём и как проверяем», но не определяет prompt или алгоритм оценки. Схема проверяет структуру, не истинность текста объяснений.

## Вход: RelevanceInput

| Поле | Смысл |
| --- | --- |
| schema_version | Строка `1.0` |
| request_id | Непустой идентификатор запуска, создаётся вызывающей стороной |
| as_of | ISO-8601 с часовым поясом; момент оценки |
| company_profile | Профиль компании; company_id обязателен, остальные исходные блоки сохраняются |
| news | Список NewsItem с уникальными id; пустой список допустим |
| bank_materials | Подготовленные материалы с фрагментами; пустой список допустим |
| options | Лимиты запуска; значения по умолчанию ниже |

`CompanyProfile` специально допускает дополнительные поля: сохраняем существующий полный профиль без переписывания чужого формата. Проверка внутреннего содержания профиля и полноты будет задачей адаптера на этапе 2. Пустое имя company_id запрещено, но одного ID для качественной оценки недостаточно.

NewsItem сохраняет имена парсера: обязательны `id`, `title`, `summary`, `link`, `published`, `source`; `author`, `categories`, `language` имеют пустые defaults. `published` — ISO-8601 с часовым поясом либо `""`. Пустые summary/link допустимы. Отсутствующий/непригодный URL должен обрабатываться инструментом как недоступный источник. Обёртку парсера `{generated_at, count, items}` будущий загрузчик преобразует в `news=items`; она не является всем входом агента.

BankMaterial: material_id, title, source_file (имя/путь первоисточника), document_date (`YYYY-MM-DD` либо null), fragments. BankFragment: fragment_id, page (с 1), text. ID фрагментов уникальны во всём запросе. Аналитику готовим разово, автоматический OCR в текущую реализацию не входит.

Options: top_k=5, max_refinement_rounds=1, max_article_fetches=15, max_article_chars=20000, counterparty_depth=1. Это стартовые технические defaults. top_k — максимум выбранных новостей, можно вернуть меньше или ни одной. Порог отбора не определён. Лимиты инструментов обязан применять будущий исполнитель, наличие поля само по себе их не обеспечивает. Весь вход не нужно отправлять одним prompt.

## Выход: RelevanceOutput

Обязательные поля: schema_version, request_id, company_id, as_of, results, selected_news_ids, warnings. Запуск, компания и момент оценки должны совпадать со входом.

В results — ровно одна запись на каждую входную новость:

| Поле | Правило |
| --- | --- |
| news_id | Исходный ID; не создавать новый |
| status | scored либо not_scored |
| relevance_score | Целое 0–100 для scored, null для not_scored |
| rank | Последовательное место от 1 для scored, null для not_scored |
| selected | Передаётся ли в подборку; false для not_scored |
| reason | Краткое основание оценки либо причина отсутствия оценки |
| company_evidence | Ссылки на поля целевой компании, тип сведения и объяснение |
| counterparty_evidence | Прямой контрагент, направление, доля, признаки, объяснение цепочки и ограничения |
| bank_evidence | Пары material_id/fragment_id из входа |
| article | Результат загрузки текста или явный статус отсутствия загрузки |
| limitations | Пробелы данных и ограничения вывода |

`selected_news_ids` перечисляет выбранные ID по rank. Порядок самого results не несёт значения. Ранг назначает код: балл по убыванию, при равенстве строковый news_id по возрастанию. Равные баллы разрешены. Не перенормировать оценки по составу подборки. Балл не является вероятностью риска.

Ориентиры для будущей настройки: 0–19 связь не установлена, 20–39 слабая, 40–59 применимо с ограниченной/неясной значимостью, 60–79 существенные основания, 80–100 первостепенная значимость. Это рабочая рубрика, ещё не откалиброванная на разметке. Критерии: связь с компанией, масштаб, косвенное влияние и временная применимость. Неопределённость показывать отдельно в limitations. Формула и веса пока не реализованы.

FeatureEvidence.field_path — JSON Pointer относительно соответствующего профиля: `/bank_relationship/products/leasing/has`. kind — source_fact, calculated либо heuristic. Существование пути проверяется; корректность интерпретации и классификации должен проверять будущий агент/оценка качества. Не ссылаться на false-флаг как на наличие продукта.

Подробные риски и рекомендации в этот контракт не входят. Следующий агент получает исходный RelevanceInput и RelevanceOutput вместе: из первого берёт профиль, новости и тексты аналитики, из второго — отбор, обоснования и загруженные статьи. При косвенных связях также передаются использованные ProfileResult и CounterpartiesResult. Ссылки нельзя передавать без этих исходных объектов. Транспорт (функция/файл/HTTP) пока не выбран.

## Инструменты — интерфейсы (контрагенты и статьи реализованы)

1. `get_counterparties(company_id) -> CounterpartiesResult`: все доступные прямые связи, не только топ-5 из профиля. Одна запись на пару (контрагент, направление). outgoing — целевая компания платит; incoming — получает. share — доля суммы в соответствующем направлении в доступном наборе, null при неопределимом знаменателе. Самоплатежи исключены. complete сообщает полноту обхода набора, а не всех операций бизнеса. Транзакции читаем один раз за запуск.
2. `get_company_profile(company_id) -> ProfileResult`: full (готовый), partial (сокращённый из CSV), unavailable (нет карточки). Возвращает sources и limitations; отсутствие профиля не отменяет платёжную связь. Обходим один уровень, без рекурсии.
3. `fetch_article(news_id) -> ArticleResult`: URL берёт из входа, а не из произвольного ответа LLM. status: ok, unavailable, not_requested. Для ok обязательны непустой text и final_url; для unavailable — error. При отсутствии загрузки text=null. Сохраняем перенаправленный final_url, флаг truncated. Исполнитель должен ограничить размер/время загрузки, проверять допустимость адресов и редиректов, не обходить ограничения доступа. Текст источника — данные, не инструкции агенту.
4. `search_bank_materials(query) -> BankSearchResult`: возвращает пары ID фрагментов из входа, query и limitations. Текст разрешается по входу. Пустой hits допустим и не является автоматически низкой релевантностью новости.

Существование профиля контрагента проверяется отдельно от существования связи. Одинаковый контрагент может иметь incoming и outgoing связи. Сведения о связях физлиц не заменяют платёжную связь в counterparty_evidence v1.

## Запуск проверок

Требуется Python 3.10+ и зависимость из локального `requirements.txt`. Проверено на Python, поставляемом со средой разработки, с Pydantic 2.14.1. Системный Python пользователя зависимость пока не содержит. Для установки использовать окружение внутри relevance_agent, не менять общий requirements.txt:

```sh
python3 -m venv relevance_agent/.venv
relevance_agent/.venv/bin/python -m pip install -r relevance_agent/requirements.txt
relevance_agent/.venv/bin/python -B -m unittest discover -s relevance_agent/tests -v
relevance_agent/.venv/bin/python -B -m relevance_agent.export_schemas
```

Проверка пары объектов в коде:

```python
from relevance_agent.contracts import RelevanceInput, RelevanceOutput, validate_exchange

request = RelevanceInput.model_validate(input_dict)
response = RelevanceOutput.model_validate(output_dict)
validate_exchange(request, response, links=links_result, profiles=profile_results)
```

Экспорт JSON Schema описывает поля и диапазоны, но не все межполевые правила: потребитель должен дополнительно соблюдать этот документ или вызывать Python-валидаторы. validate_exchange проверяет покрытие входных новостей, ссылки на поля и банковские фрагменты, идентичность запуска, top_k, связи и доли контрагентов. Он не проверяет истинность цитат, актуальность события, достижение лимитов инструментов или качество ранжирования.

Основа реализации: [модели Pydantic](https://docs.pydantic.dev/latest/concepts/models/) и [валидаторы](https://docs.pydantic.dev/latest/concepts/validators/).

Этап 2 выполнен: загрузчики и build_relevance_input(). Примеры запуска — в README.md. Основной запуск теперь через SingleNewsInput и graph.score_news().


## Основной событийный контракт (1.0-single)

Источник схем: `single_contracts.py`, экспорт: `schemas/SingleNewsInput.json` и
`schemas/SingleNewsOutput.json`. Граф принимает одну новость, не список.

Вход: `company_id`, `news: NewsItem`, необязательные `request_id`, `as_of`, `options`.
Профиль, все прямые контрагенты, статья и подготовленная аналитика собираются внутри графа.
Параметр `top_k` из совместимого RunOptions не используется для единичной оценки.

Выход: исходная новость/компания/момент, `status=scored|not_scored`, `assessment`.
При успехе assessment содержит `relevance_score`, `reason`, `company_evidence`,
`counterparty_evidence`, `bank_evidence`, `limitations`. При отказе assessment=null.
Баллы не зависят от других новостей. `rank` и `selected` отсутствуют; бизнес-порог
и сортировка относятся к последующей обработке ленты.

Также выход содержит `article`, `company_profile`, `counterparties`,
`counterparty_profiles`, `bank_materials`, `bank_metadata`, `warnings`, `model`,
`model_calls`, `usage`. Следующий агент получает исходные доказательства вместе с оценкой.
Каждая цитата банка ссылается на переданный material_id + fragment_id, признаки —
на существующий JSON Pointer; ссылки на контрагентов проверяются по платёжному набору.
Техническая проверка не подтверждает смысловую достоверность вывода модели.


### Дополнение: полный текст из парсера

NewsItem расширен необязательным full_text (по умолчанию пустая строка). Старые входы
остаются допустимыми. ArticleResult расширен text_source: agent_fetch (по умолчанию)
или upstream_parser. При ok + agent_fetch по-прежнему обязателен final_url; при
upstream_parser он может быть null, поскольку новый парсер не передаёт редиректы.
Старые потребители с запретом неизвестных полей должны обновить схемы перед интеграцией.
JSON-схемы переэкспортированы. Версии существующих конвертов сохранены.


### Дополнение: быстрый режим отбора

Выходной контракт не изменён. assessment после ремонта: company_evidence и
counterparty_evidence — не больше 3, limitations — не больше 2, bank_evidence всегда [].
counterparty_evidence.share берётся из платёжного инструмента. Отброшенные моделью ссылки
перечисляются в warnings. Запрос к модели — внутренний формат (компактные карточки),
не часть контракта обмена; полный профиль, связи и статья остаются в SingleNewsOutput.

### Дополнение: релевантность через каналы влияния (scoring_version = channels-v1)

Релевантность — сила возможного влияния события на деньги компании через канал передачи,
а не близость события к её отрасли. Событие другой отрасли релевантно, если меняет
цены на входе, спрос покупателей, рынок, стоимость денег, валюту, правила, логистику или
контрагентов. Роль пользователя не учитывается.

Разделение ответственности:
- модель (graph.SYSTEM) только разбирает событие: каналы, shock (weak/notable/strong),
  direction, horizon (now/months/years), mechanism (цепочка до 3 звеньев),
  event_confidence; балл модель не ставит;
- код (scoring.py) берёт подверженность компании каналу из профиля и считает балл.

Каналы: input_costs, customer_demand, market_structure, cost_of_money, fx_trade,
regulation, logistics, counterparties.

Формула: impact = exposure × SHOCK[shock] × HORIZON[horizon];
relevance_score = 100 × (1 − Π(1 − impact)) по трём сильнейшим каналам, округление вверх от 0,5.
SHOCK: weak 0.25, notable 0.5, strong 0.8. HORIZON: now 1.0, months 0.85, years 0.6.
exposure: сильнейшая sensitivity канала (высокая 1.0, средняя 0.7, низкая 0.4,
kind=heuristic); без признака — базовая (input_costs 0.3, customer_demand 0.4,
market_structure 0.8 по ОКВЭД, cost_of_money 0.3, fx_trade 0.2, regulation 0.4,
logistics 0.3; kind=calculated). Отсутствие данных не считается нулевой подверженностью.
Канал counterparties: конкретный прямой контрагент со связью и профилем, exposure =
0.3 + 0.7 × доля платежей (не доля выручки); без контрагента — только теги
supplier/customer_concentration и holding. Все числа — рабочие, не откалиброванные веса.

В assessment добавлены необязательные поля: channels (ChannelImpact: исходный разбор
модели + exposure, exposure_basis, exposure_kind, impact, counted), event_confidence
(достоверность события, в балл не входит) и scoring_version. company_evidence и
counterparty_evidence строятся кодом из exposure_basis, поэтому всегда ссылаются на
существующие поля. Если ни один канал не прошёл проверку — повтор, а не фиктивный ноль;
пустой channels — честный 0. Схемы переэкспортированы; старые поля не изменены.


### Дополнение: channels-v2 (поправки к формуле, 26.10.2026)

impact = exposure × SHOCK[shock] × HORIZON[horizon] × CONFIDENCE[event_confidence];
CONFIDENCE: high 1.0, medium 0.8, low 0.6 (неизвестное значение → medium с предупреждением).
relevance_score = 100 × (1 − Π(1 − w_k × impact_k)) по трём сильнейшим каналам,
w = (1.0, 0.6, 0.4): один драйвер, увиденный через два канала, не считается дважды.
Подверженность из sensitivities, выведенных по странам ФТС (source_fields FTS_FLAG /
FTS_COUNTRY_NAME), умножается на 0.7: валюта и направление торговли — догадка.
Базовая подверженность market_structure — 1.0 (основной рынок по ОКВЭД).
Остальное как в channels-v1. Веса рабочие, проверены на трёх новостях, не откалиброваны.


### Дополнение: channels-v3 (26.10.2026)

SHOCK.weak = 0.15 (было 0.25): одна слабая косвенная цепочка остаётся ниже 20 баллов.
Скидка за догадку обобщена (GUESS_DISCOUNT): если ВСЕ source_fields признака — догадка,
подверженность умножается: страны ФТС (FTS_*) ×0.7 — валюта и направление не известны;
наличие продукта банка (CL_PRODUCT_*) ×0.8 — объём долга/депозита/гарантий не известен.
Признак с основанием по ОКВЭД или платежам скидку не получает.
Таймаут модели: ровно один повторный вызов (запись в warnings); другие сетевые ошибки
не повторяются. Максимум вызовов на новость — 3 (таймаут + повтор после проверки).


### Дополнение: сводка контрагентов в запросе модели (26.10.2026)

Модель получает не карточку каждого контрагента, а сводку: without_profile (число, суммарные
доли) и by_industry по основному ОКВЭД (до 12 отраслей, top-3 по доле, хвост — other_industries).
Канал counterparties по-прежнему проверяется по всем связям инструмента: модель может назвать
любой id со связью и профилем; exposure и доля берутся из CounterpartiesResult. Выходной
контракт не изменён: полный список связей и профилей остаётся в SingleNewsOutput.


### Дополнение: channels-v4 — стабилизация шока (26.10.2026)

SHOCK: weak 0.15, moderate 0.3, notable 0.5, strong 0.8. Промежуточный moderate уменьшает
скачок балла при пограничном выборе модели; в prompt — «при сомнении выбери нижний уровень».
Каждый канал содержит shock_basis — дословную цитату из новости (до 200 символов), которая
оправдывает уровень шока. Код проверяет её по title + summary + тексту статьи (нормализация
регистра, ё, кавычек и пробелов; либо ≥80% слов от 4 букв). Если цитаты нет или она не найдена,
шок выше weak понижается до weak, исходный уровень сохраняется в model_shock, в warnings —
запись. ChannelImpact дополнен необязательными shock_basis, basis_verified, model_shock.
